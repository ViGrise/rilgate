# hashwx-wasm

Raw C-style browser ABI for the workspace Apache-2.0 HashWX implementation.
Behavior comes from the specification cited in
[`hashwx-core`](../hashwx-core/README.md). There is no wasm-bindgen glue or BigInt
requirement. Every nonce, target and hash is represented by two u32 halves,
low half first. Hash and nonce buffers are little endian.

Build and stage with `cargo xtask build-wasm`. The artifact is
`web/static/js/solvers/hashwx/hashwx_wasm.wasm`, alongside RandomX. This build
uses `wasm32v1-none`, `no_std` and the `dlmalloc` allocator for a WebAssembly
1.0 baseline. Install the target with `rustup target add wasm32v1-none`. The artifact is ignored
by git. The browser adapter, solver and worker are in the same directory.

## ABI

Pointers and lengths use wasm32 i32 slots. Handles are nonnegative i32 values.
Function status is 0 on success and -1 for invalid handles, invalid seed lengths,
or an exhausted range. Module accessors return zero for invalid handles.

| Export | Parameters | Result / output |
| --- | --- | --- |
| `memory` | - | Interpreter linear memory |
| `hx_alloc` | - | Pointer to a zeroed 32-byte caller buffer |
| `hx_free` | `ptr` | Frees that buffer; no result |
| `hx_seed` | `challenge_ptr, batch_lo, batch_hi, out_ptr` | Writes 32 seed bytes as SHA-256(challenge || batch in little endian) |
| `hx_create` | `seed_ptr, seed_len` | Instance handle, or -1; seed_len must be 32 |
| `hx_hash` | `handle, nonce_lo, nonce_hi, out_ptr` | Status; eight-byte hash at out_ptr |
| `hx_search` | `handle, nonce_lo, nonce_hi, count, target_lo, target_hi, out_ptr` | Status; 16-byte nonce followed by hash on success |
| `hx_module_ptr` | `handle` | Pointer to generated module bytes |
| `hx_module_len` | `handle` | Generated module byte length |
| `hx_destroy` | `handle` | Status; releases instance and module bytes |

Search tests consecutive nonces, modulo 2^64, for the first hash strictly less
than target. A zero target always exhausts the range. Zero count searches
nothing. Output stays unchanged on failure. One search call covers a batch
without a JavaScript call per nonce. Both interpreter and generated module
implement these rules.

The caller must provide valid readable/writable memory for each pointer and
free each hx_alloc buffer exactly once. Refresh JavaScript memory views after
allocations, instance creation or module requests, because linear memory can grow. Code generation runs when `hx_module_ptr` or `hx_module_len` first requests it.
The instance
copies the seed; the seed buffer can be freed after creation. Module bytes are
owned by the handle until destruction. Copy them before retaining a JavaScript
view across memory growth. Handles may be reused after destruction.

Instantiate the generated bytes with `WebAssembly.instantiate(bytes, {})`.
The generated module owns a separate, fixed one-page memory and exports
`hash(nonce_lo, nonce_hi)` and
`search(nonce_lo, nonce_hi, count, target_lo, target_hi)`. Hash output is at 16400;
the matching nonce location is exported as the immutable `result_ptr` global. Both return 0/-1 status. The module needs no
interpreter handle or imported memory and remains usable after hx_destroy.
See the core README and `HashWx::wasm_module` for the complete memory layout.

## Validation and benchmark

```sh
cargo xtask build-wasm
cargo xtask build-web
cargo test -p hashwx-core -p hashwx-wasm --locked
node --test tests/hashwx-wasm.test.mjs
node scripts/bench-hashwx-wasm.mjs
```

A strict validator checks the staged artifact against WebAssembly 1.0 and
checks that it has no host imports. Tests run all four Appendix F vectors through both paths, then compare 4096
hashes across 64 pseudorandom seeds and exercise range-search boundaries.
The benchmark reports 463 and 65536 nonces per seed, including per-seed
generation and generated-module compilation/instantiation costs. Initial
loading of the shared interpreter artifact is excluded from the per-seed cost.
